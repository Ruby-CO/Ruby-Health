# Ruby Health — data model doctrine

## What this file is

The written-down version of the data model: what each entity is for, how they
connect, and the naming rules everything follows. It is **living
documentation** — when the schema changes, this changes in the same PR.

It is deliberately not a list of problems. Problems live in
`schema-audit.md`, which the `data-model` agent rewrites on each run. This
file is what "correct" looks like; the audit is the distance from it.

The diagram of all of this is `schema.mermaid`, regenerated by the same agent.

**Read the Settled decisions section before proposing a change.** Several
things here look like oversights and are not.

---

## Where the data actually lives

Today: **Notion**, one database per entity. That choice is about compliance,
not fit — the prototype holds only synthetic data, so it needs no BAA, no
encryption at rest, and no audit logging. A real patient record could not sit
here.

Tomorrow: **Postgres**, or whatever the production system brings.

The seam between the two is `backend/src/repository/Repository.js` — an
interface where every method throws until a concrete repository implements
it. `NotionRepository.js` is the only file in the project that may import a
Notion client or know that a Notion page ID exists. Nothing else —
`server.js`, the pipeline, the eval suite — may reach past the interface.
That boundary is the whole reason a store this unusual is acceptable: swapping
it costs one file, not a rewrite.

## The entities

Seven, plus one that is modelled nowhere (see the last row).

| Entity | Notion DB | ID prefix | What it is |
|---|---|---|---|
| **Patient** | Patients | `P001` | A person on file: name, date of birth, and — optionally — sex and a snapshot of insurance status. |
| **Case** | Cases | `C001` | One episode of care. A patient can have several open at once — a broken arm and a pregnancy are separate stories that must not merge. |
| **Encounter** | Encounters | `E001` | One visit inside a case. The unit the pipeline runs on. |
| **Artifact** | Artifacts | `A001` | One version of one pipeline stage's output for one encounter. Append-only. |
| **Claim** | Claims | `CL001` | A claim built from a specific artifact. Corrections and secondary filings are new rows chained to the original. |
| **PayerFeedback** | Payer Feedback | `PF001` | What came back after submission — a 277CA acknowledgment or an 835 remittance. |
| **Document** | Documents | `D001` | A file attached to a patient, optionally scoped to a case. A reserved slot: the schema exists, the upload and extraction UI does not. |
| *ProviderProfile* | — | `default` | The billing provider's NPI, tax ID, taxonomy and address. **Not an entity** — a JSON file on ephemeral disk (`backend/src/providerProfiles.js`), keyed by `providerId` so it can become a table without touching call sites. `Claim.provider_id` and `Artifact.provider_id` point at it. |

## How they connect

```
Patient ─┬─< Case ─< Encounter ─┬─< Artifact ─< Claim ─< PayerFeedback
         │                      └─< Claim              ↑
         └─< Document                Claim ─< Claim ───┘  (parent_claim_id)
```

In words:

- A **patient** has many **cases**; a case belongs to exactly one patient.
- A **case** has many **encounters**, in chronological order.
- An **encounter** carries a denormalized `patient_id`. It is looked up from
  the case, never accepted from the caller, so the two cannot drift.
- An **encounter** has many **artifacts** — every version of every stage.
  `(encounter_id, stage)` plus `version` identifies one; version
  auto-increments from the highest existing version for that pair.
- A **claim** points at both the encounter it bills and the exact artifact it
  was built from. That second pointer is the audit trail: a submitted claim
  still resolves to the record it came from, even after the provider edits
  the encounter afterwards.
- A **claim** may point at a **parent claim**. A chain is every claim reachable
  from the same original — corrections and secondary filings, not necessarily
  one straight line. All claims in a chain hang off the same encounter, which
  is why `getClaimChain` traverses within an encounter rather than across the
  whole Claims database.
- A **claim** collects **payer feedback** rows, oldest first.
- A **claim** and an **artifact** each carry a `provider_id`: who the row was
  created for. It is a soft FK to the provider profile, stamped at creation
  from `resolveProviderId()` in `server.js` — the one seam where a real
  identity source would attach. Today every row says `default`; rows written
  before the field existed read back as `null`, and nothing requires it. A
  correction or appeal inherits the original claim's provider. It is
  independent of `parent_claim_id` and plays no part in chain traversal.
- A **document** belongs to a patient and optionally narrows to a case. It
  attaches to no encounter.

**Every foreign key is soft** — a plain text property holding another row's
business ID, not a Notion relation. That is on purpose: it keeps the adapter's
behaviour close to what the Postgres implementation will do, and it means a
relation type does not have to be unwound later. The cost is that nothing
enforces the reference. `NotionRepository` checks the parent exists at write
time; nothing re-checks it afterwards.

## Naming conventions

**Two vocabularies, one mapping.** Notion properties are `snake_case`; the
domain objects the rest of the app sees are `camelCase`. The translation
happens in exactly two places per entity — a `parse*` function (read) and a
`create*`/`update*` method (write). They are written separately, so a property
added to one and not the other is invisible until something breaks. Change
both, together, always.

**Identifiers.**
- Every entity's Notion **title** property is its business ID, named
  `<entity>_id` — `patient_id`, `claim_id`, `feedback_id`.
- Foreign keys reuse the referenced entity's name exactly: a Case's
  `patient_id` is the same string as that Patient's `patient_id`. Never
  `patient`, never `patientRef`.
- IDs are `PREFIX` + three zero-padded digits, minted by scanning existing
  titles for the highest number.

**Types.**
- Short free text → `rich_text`. Long free text and JSON → `rich_text`,
  chunked at 2000 characters (Notion's per-item cap) and rejoined on read
  via `richTextAll`.
- A closed vocabulary → `select`. Never free text.
- Dates → `date`, stored as `YYYY-MM-DD` when the app sets them.
- Money and counts → `number`.
- `created_at` is read from a `created_time` property, falling back to the
  page's own `created_time`. Nothing writes it.

**Vocabularies** (the `select` values) are declared as module constants at the
top of `NotionRepository.js` and validated on write: `STAGES`,
`CREATED_BY_VALUES`, `CLAIM_TYPES`, `CLAIM_STATUSES`, `DOCUMENT_SOURCES`,
`FEEDBACK_TYPES`, `PATIENT_SEXES`, `INSURANCE_STATUSES`. **A new select property gets a constant and a write-time
check.** Two current properties do not have one — `claim_status` and
`recommended_route` on PayerFeedback take their values from
`analyzeRemittance.js` instead, so the repository cannot reject a value it
does not know.

**Absent values.** A `select` left unset means "not applicable" and is written
by omitting the property, not by writing a placeholder — an acknowledgment
carries no verdict, and an empty select says that honestly. A `rich_text`
foreign key with nothing in it is written as `""` and parsed back to `null`.
These two are inconsistent with each other; the audit may say so.

## Status vocabularies

| Where | Values |
|---|---|
| `Patient.sex` | `male`, `female`, `unknown` — PHI. Optional; unset means not recorded. `populateClaim` maps to the `M`/`F`/`U` the 837P carries. |
| `Patient.insurance_status` | `self_pay`, `insured`, `pending` — PHI-adjacent. Optional. A **snapshot**, not a history: a change overwrites. Eligibility (270/271) is a separate, unbuilt entity. |
| `Case.status` | `open`, `closed` |
| `Encounter.status` | `draft` (only value written today) |
| `Artifact.stage` | `transcript`, `facts`, `codes`, `claim` |
| `Artifact.created_by` | `system`, `provider_edit` |
| `Claim.claim_type` | `original`, `corrected`, `secondary` |
| `Claim.status` | `draft`, `submitted`, `accepted`, `rejected`, `denied`, `pending` |
| `PayerFeedback.feedback_type` | `acknowledgment`, `remittance` |
| `Document.source` | `upload`, `fax`, `ehr_sync` |
| `Document.extraction_status` | `none` (only value written today) |

`Claim.status` also drives the UI: it decides whether an encounter is
editable (anything past `draft` locks the record) and which actions a claim
offers in History.

## Settled decisions

These look wrong and are not. **Do not report them as findings.** If the code
has drifted from what one of these says, report the drift.

**`case_title`, not `title`.** Notion's API key `title` always refers to
whichever property is type `title` — `case_id` here — regardless of display
name. A property literally named `title` would be unreachable. The domain
field is still `title`.

**The stage key is `transcript`, the UI says "Context".** The rename is
deliberate and deliberately incomplete. `transcript` is a Notion select option
carried by every artifact already written, and it is also the API field name.
Renaming the stored key is a data migration; renaming the API field needs a
versioned endpoint. Either is fine — in the same change, not before it.

**Soft text foreign keys, not Notion relations.** See "How they connect".

**Sequential, human-readable IDs.** `P001` is enumerable and unsafe for
production, which will mint UUIDs. It is kept here because a demo where you
can read the IDs aloud is worth more than one where you cannot, and the
production repository will not use this code path at all.

**Artifacts are append-only.** An edit writes a new version with
`created_by: "provider_edit"`. Never an overwrite — the revision list is the
trail, and a submitted claim must still resolve to the artifact it was built
from.

**Document has a schema and no UI.** The slot is reserved for PDF and Word
uploads, which need a parser and a file store before they can exist. An empty
slot is not an unfinished feature.

**No encryption at rest, no audit log, no retention policy.** Prototype, and
the reason synthetic-only is a hard rule rather than a preference. The audit
should still list the missing compliance fields — knowing the size of the gap
is the point — but their absence is not news.

## Changing the schema

1. Update `NotionRepository.js` — the `parse*` function **and** the
   `create*`/`update*` methods.
2. Update `Repository.js` if the interface shape changes.
3. Add or extend the vocabulary constant if it is a `select`.
4. Update this file in the same PR.
5. If an existing row would need rewriting, say so in the PR description.
   There is no migration tooling; a migration here is a script someone runs
   once and watches.
6. Re-run the `data-model` agent so the diagram and audit reflect the change.

**Nothing reminds you about step 6 automatically, on purpose.** The *Schema
docs* workflow (`.github/workflows/schema-docs.yml`) will tell you whether a
schema change refreshed `docs/data/`, but it is manual: Actions → *Schema docs*
→ **Run workflow**. It runs no model and regenerates nothing — it reads a diff
and reports. A pipeline change alone leaves a note rather than a failure,
because a file path cannot tell a renamed field from a reworded prompt.

That is a deliberate choice rather than an oversight: the data-model tooling
does not act unless a person asks it to, and that covers noticing as well as
auditing. The workflow file documents how to put it back on automatic.
